## 1. Проблема

Существующие инструменты не отвечают на базовые вопросы владельца портфеля.

- **Actual Budget** ведёт доходы и расходы, но не знает, что такое позиция, лот и купон.
- **Snowball Income** умеет акции, но облигации и депозиты для него второстепенны.
- **Excel** — отказ от него является исходным требованием.

Конкретные дефекты, из-за которых цифрам существующих сервисов нельзя верить:

1. **YTM выдаётся за фактическую доходность владельца.** Сама метрика корректна: это ставка, дисконтирующая обещанные потоки к текущей цене, и как рыночная конвенция для сравнения выпусков она работает. Проблема в интерпретации: реализованной сложной доходностью YTM становится только при реинвестировании каждой выплаты по той же ставке. Купон приходит деньгами, ставки к этому моменту другие. Сервисы не показывают, при каком допущении их цифра верна.
2. **Налоги не учитываются.** Ни НДФЛ с купона и дивиденда, ни налог при продаже, ни ЛДВ, ни ИИС, ни налог с процентов по вкладам. Доходность до налога не является доходностью владельца.
3. **Купонный и дивидендный доход как отдельный поток практически не отслеживается.**
4. **Граница портфеля определяется учреждением, а не владельцем.** Перевод со вклада на брокерский счёт брокер считает пополнением, потому что вклад вне его периметра. Собственные пополнения выглядят как заработок.
5. **Лоты подменяются средней ценой.** Брокер показывает позицию одной строкой со средней ценой, а налоговую базу считает по FIFO (ст. 214.1 НК РФ). Связь между двумя числами нигде не объясняется. Без лотов ЛДВ не вычисляется в принципе.
6. **Не различаются «что у меня есть сейчас» и «что будет, если додержу».** Начисленные, но не выплаченные проценты по вкладу при досрочном расторжении теряются; НКД по облигации при продаже выплачивается покупателем. Два актива с одинаковой ставкой ведут себя по-разному, и разницу не показывает никто.

Вопросы, на которые система обязана отвечать:

- Сколько я инвестировал в этом году?
- Сколько заработал — после налогов, с разложением на источники?
- Был ли LQDT правильным решением по сравнению с альтернативой?
- Сколько денег я реально получу, если закрою всё сегодня?

## 3. Архитектура

### 3.1 Функциональное ядро, императивная оболочка

Ядро **не делает ввода-вывода** — ни напрямую, ни через порты-трейты. Оболочка собирает данные, ядро считает, оболочка сохраняет результат.

```
                 входы (взаимозаменяемы)
   iaam-server (REST) · iaam-cli · позже MCP, Tauri
                          ↓
   iaam-app     сценарии, порты ввода-вывода, кэш, снимки
                          ↓
   адаптеры     iaam-store (SQLite) · iaam-market (MOEX/ЦБ) · iaam-ingest (парсеры)
                          ↓
   iaam-core    чистые функции: (состояние, события, контекст) → результат
                sync, без I/O, без async, без Mutex, без f64 (§17.3)
```

**Ядру не нужны порты ввода-вывода**, потому что оно получает готовый срез данных: журнал личного портфеля — тысячи событий, загружается в память за миллисекунды. `TaxContext` (§3.2) устроен ровно так.

**Но «весь журнал в память» — умолчание, а не архитектурный инвариант.** Нагрузка растёт не от журнала, а от произведения `даты × инструменты × сценарии × контуры × версии правил`: пятнадцать лет ежедневного ряда по нескольким сотням инструментов с несколькими сценариями ставок дают уже миллионы оценок. Если публичная функция ядра сразу примет вид `calculate(все_события, все_цены, все_контексты)`, инкрементальность позже потребует смены интерфейсов.

Поэтому ядро с самого начала умеет работать со снимками:

```rust
project(snapshot, events_since_snapshot, context) -> Projection
advance(previous, ordered_events, context_delta)  -> Projection
value_range(projection, market_slice, date_range) -> NavSeries
```

Ядро чисто строит снимок, чисто продвигает его последовательностью событий, проверяет версию и хеш входного состояния и умеет сделать полный пересчёт с нуля как эталон. **Снимки и кэш хранит оболочка** — ядро остаётся без состояния.

**Потоковый импорт живёт в `iaam-ingest`:** парсер отдаёт ограниченные пачки строк в область приёмки; по завершении документа оболочка формирует нормализованную неизменяемую пачку для ядра и атомарно публикует принятые события. Большой отчёт никогда не попадает в ядро одним объектом.

**Параллельные сценарии не копируют базу.** Базовая проекция неизменяема и разделяется через `Arc`; сценарий передаёт только наложение:

```rust
ScenarioInput {
    base: Arc<Projection>,
    market_overrides: ...,
    tax_rule_override: ...,
    rate_path: ...,
}
```

Копируются только изменённые входы и результаты. Это существенно: налоговое планирование и флоатеры требуют многих сценариев одновременно.

### 3.2 Модули, стратегии и внедрение зависимостей

#### Граф зависимостей

```
                    iaam-core
                 ↑      ↑      ↑
          iaam-store  iaam-market  iaam-ingest
                 ↖      ↑      ↗
                    iaam-app
                    ↑        ↑
              iaam-server  iaam-cli
```

| Крейта | Зависит от | Ответственность |
|---|---|---|
| `iaam-core` | — | доменные типы, журнал, проекции, лоты, доходность, налоги, тождество результата |
| `iaam-store` | core | SQLite, миграции, архивный бандл |
| `iaam-market` | core (только доменные типы) | MOEX, ЦБ РФ, кэш, устойчивость, история цен |
| `iaam-ingest` | core | разбор источников, сверка, статусы достоверности |
| `iaam-app` | core + store + market + ingest | сценарии, порты, снимки, кэш |
| `iaam-server` | app | axum, REST, OpenAPI, аутентификация |
| `iaam-cli` | app | локальные команды |

**`iaam-server` не зависит напрямую от `iaam-store` и `iaam-market`** — кроме сборки конкретных реализаций в точке сборки. Иначе заявленная взаимозаменяемость транспорта фиктивна: обработчики HTTP начнут оркестрировать адаптеры, а CLI продублирует эту оркестрацию.

#### Никакого общего крейта «shared» / «common» / «utils»

Доменные типы (`Money`, `InstrumentId`, даты, события) принадлежат `iaam-core`. Транспортные и хранилищные представления остаются у себя: REST DTO — в `iaam-server`, разобранные записи источников — в `iaam-ingest`, ответы MOEX — в `iaam-market`, строки таблиц — в `iaam-store`. Преобразование в доменные типы происходит на границе.

Общий крейт типов выглядит удобным, но быстро превращается в свалку DTO, ошибок, конфигурации и транспортных структур — и тогда формально независимое ядро оказывается зависимым от слоя, который знает обо всём.

#### Доменные стратегии — это не порты

Отказ от `EventStore` внутри ядра не означает отказа от абстракций поведения. Версионированное списание лотов (§4.12), налоговые правила по годам (§9.1), база начисления дней и политика оценки (§5.4) — **доменные стратегии**, а не ввод-вывод. Без явного механизма подключения «версионированность» останется декларацией, а в проекциях разрастётся `match year`.

Стратегия передаётся в ядро как неизменяемый вход, поэтому чистота не нарушается:

```rust
trait LotDisposalRule {
    fn id(&self) -> RuleId;
    fn apply(&self, input: &LotDisposalInput) -> LotDisposalResult;
}

trait TaxRuleSet {
    fn id(&self) -> TaxRuleSetId;
    fn calculate(&self, input: &TaxInput) -> TaxResult;
}

struct RuleRegistry {
    lot_rules: BTreeMap<LotRuleVersion, LotRule>,
    tax_rules: BTreeMap<(TaxYear, TaxBaseKind), TaxRuleSet>,
}
```

Плагины в рантайме не нужны, поэтому реестр закрытый. **Идентификатор применённой версии правила входит в результат и в след аудита** — иначе цифру нельзя воспроизвести.

#### Граница внедрения зависимостей

Гибрид обобщений и трейт-объектов без установленной границы вырождается: `App<S, M, I, C, A, R, J, ...>` расползается по обработчикам, тестам и конструкторам, а параллельное существование двух моделей DI усложняет код. Граница фиксируется:

| Уровень | Механизм |
|---|---|
| Доменные алгоритмы в `iaam-core` | обобщения или закрытые enum-стратегии |
| Сервисные зависимости `iaam-app` | `Arc<dyn Store>`, `Arc<dyn MarketData>`, `Arc<dyn Clock>` |
| Внутри отдельного адаптера | обобщения допустимы, но не параметризуют `App` |

Точка сборки создаёт один `AppServices`; обработчики получают `Arc<AppServices>`. DI-фреймворк не используется: неявность плохо сочетается с кодом, который пишет агент.

#### Граница async

`iaam-market` естественно асинхронен; `rusqlite` — блокирующий. Смешение даёт два отказа: async протекает через весь `iaam-app`, а блокирующий SQLite останавливает исполнитель axum.

- `iaam-core` — строго синхронный.
- Сценарии `iaam-app` могут быть асинхронными.
- Объектобезопасные порты существуют **только** в `iaam-app`.
- SQLite вызывается через выделенный блокирующий исполнитель или `spawn_blocking`; границы транзакций описаны явно.
- Механизм async-трейтов выбирается **один** и закрепляется архитектурным тестом. Смешение `async_trait`, RPITIT и ручных boxed futures без необходимости запрещено.

#### Налоговый контекст

Налоговому расчёту нужны курсы ЦБ на даты, признаки обращаемости и параметры инструментов. Зависимости от `iaam-market` при этом нет: налоговая функция принимает подготовленный неизменяемый **`TaxContext`** (курсы с источником и датой, классификации инструментов, режимы счетов, перенесённые убытки). Добыча данных остаётся в оболочке, provenance входит в расчёт.

### 3.3 Хранилище

SQLite — файл базы является полным рабочим состоянием. Доступ через слой, не закрывающий дорогу к PostgreSQL. **Копия файла не является полноценным бэкапом** — см. §14 про архивный бандл.

### 3.4 Точность и денежные типы

Разделяются две категории величин:

**Проведённые суммы (posted money)** — то, что реально прошло по счёту. Целые числа в минимальных единицах валюты, в опубликованной источником точности. Это факты, их нельзя пересчитывать.

**Расчётные величины (calculation amounts)** — цены в процентах номинала, НКД на одну бумагу, ставки, курсы, разнесение комиссии, промежуточные агрегаты. Decimal с явным масштабом. `float` запрещён везде.

**Политика округления:** промежуточные агрегаты не округляются; округление происходит однократно на границе представления; порядок округления фиксирован и покрыт тестами (§6.6).

Количество бумаг — Decimal с явным масштабом (крипта дробная, дробные остатки после сплитов возможны).

## 4. Журнал фактов

### 4.1 Envelope события

Общая оболочка обязательна с первого коммита — её отсутствие потребует переинтерпретации уже записанных фактов.

```
eventId
eventType
schemaVersion
dates: { tradeAt?, settledAt?, cashPostedAt?, entitlementAt?, paidAt?, taxPeriod? }
recordedAt
effectiveOrder          детерминированный порядок при равных датах
identities: { ownerId, accountId, custodyId?, instrumentId?, sourceId }
legs: [ ... ]           типизированные ноги движения
provenance: { rawHash, sourceOperationId?, parserVersion?, documentRef?, rowLocator? }
idempotencyKey
relation: { type: none | reversal | replacement, targetEventId? }
confidence: known | estimated | unknown
```

### 4.2 Семантические даты

Одной даты недостаточно. Сделка 30 декабря с расчётами 3 января попадает в другой налоговый год; дивиденд имеет дату отсечки и дату выплаты; налог имеет дату удержания и налоговый период, к которому относится.

| Дата | Смысл |
|---|---|
| `tradeAt` | заключение сделки |
| `settledAt` | расчёты, переход прав |
| `cashPostedAt` | движение денег по счёту |
| `entitlementAt` | дата, определяющая право на выплату (отсечка) |
| `paidAt` | фактическая выплата |
| `taxPeriod` | налоговый период, к которому относится удержание |

Заполнять все на первом этапе не требуется; **схема обязана их допускать** без переинтерпретации.

### 4.3 Типизированные ноги движения

Событие не является одной неразложимой суммой. Минимальный набор ног:

- **cash leg** — денежное движение;
- **security quantity leg** — движение количества бумаг;
- **principal/nominal leg** — движение непогашенного номинала;
- **fee/tax leg** — комиссии и налоги.

Полноценный двойной учёт на старте не строится, но разложение на ноги обязательно: без него амортизация, НКД и разнесение комиссии невосстановимы.

### 4.4 Сохранение сырых значений

Записываются без потери информации: количество, цена, gross amount, net amount, комиссия, НКД, валюта каждой величины, исходный знак, исходная точность, ссылка на строку источника. **Записывать только нормализованную итоговую сумму запрещено** — из неё нельзя восстановить разнесение.

### 4.5 Раздельные идентичности

`owner`, `account` (денежный счёт), `custody` (место хранения бумаг), `instrument`, `source`. Брокерский счёт не является одновременно владельцем, денежным счётом и местом хранения: перевод бумаг между депозитариями внутри одного брокера — реальная операция.

### 4.6 Типы событий

| Событие | Содержание |
|---|---|
| `trade` | покупка/продажа: инструмент, количество, цена, комиссия, валюта, НКД |
| `cash_in` / `cash_out` | пересечение границы контура |
| `cash_transfer` | движение денег между счетами внутри контура (пара половин) |
| `security_transfer` | перевод бумаг между счетами/депозитариями: количество, custody, ссылки на исходные налоговые лоты, подтверждённость затрат, состояние «в пути» |
| `income` | купон, дивиденд, **фактически выплаченные или капитализированные** проценты |
| `fee` | комиссия, не привязанная к сделке; поле `origin` для источника |
| `fx_conversion` | конвертация валюты |
| `tax_assessed` | признание налогового обязательства |
| `tax_withheld` | удержание налоговым агентом |
| `tax_paid` | самостоятельная уплата |
| `tax_refunded` | возврат излишне удержанного |
| `tax_credit_applied` | зачёт |
| `deposit_contract` | условия вклада и их версии (см. §8) |
| `valuation` | ручная оценка неликвида на дату |
| Семейство корпоративных действий | см. §4.7 |
| `opening_position` / `opening_cash` | восстановленное начало (см. §10.6) |

Все налоговые события несут `taxPeriod`, `taxBaseCategory`, `taxAgentId`, валюту и ссылку на исходные доходы.

### 4.7 Корпоративные действия — семейство, а не тип-мешок

Один универсальный `corporate_action` превращается в невалидируемый JSON без инвариантов. Вместо него типизированное семейство, каждый член которого объявляет входные и выходные инструменты, коэффициент, денежную компенсацию, дату прав и правило переноса налоговой стоимости:

`split` · `reverse_split` · `redemption` · `partial_redemption` (амортизация) · `merger` · `spin_off` · `isin_change` · `conversion` · `delisting` · `compulsory_redemption` · `rights_issue` · `distribution_in_kind` · `fractional_settlement` · `bankruptcy_writeoff`

**Оферта не является корпоративным действием.** Это право предъявить бумагу в заданное окно. Условия оферты хранятся в инструменте; фактами являются поданная заявка и совершённый выкуп. Плановая проекция обязана указывать, какой сценарий выбора владельца она предполагает.

### 4.8 Неизменяемость и исправления

События неизменяемы. Модель исправлений — **reversal + replacement**: исправляющее событие сторнирует исходное и добавляет новое, обе записи остаются в журнале.

Разрешение конфликтов детерминировано: при двух конкурирующих исправлениях порядок определяется `effectiveOrder`, а не порядком импорта. Ветвление цепочек исправлений запрещено. Отмена без замены — отдельная операция (`reversal` без последующего `replacement`), а не «пустое исправление».

Это делает штатными сценарии, ломающие CRUD-модель: правку задним числом и пересчёт истории при изменении налоговых правил.

### 4.9 `unknown` как полноценное значение

Неизвестная дата приобретения, налоговая стоимость, классификация или налоговый режим остаются неизвестными. Заполнение фиктивными нулями запрещено: отчёт должен уметь вернуть диапазон или `not_computable`, а не точную цифру, построенную на выдуманных данных.

### 4.10 Контуры

**Контур определяет владелец, а не учреждение.** У каждого счёта — принадлежность к инвестиционному контуру.

- Перемещение внутри контура не является ни взносом, ни выводом; на доходность не влияет, меняется только аллокация.
- **Контуров несколько.** Один перевод внутренний на уровне «весь капитал» и внешний на уровне «биржевой портфель». Обе точки зрения корректны, поэтому контур — параметр отчёта, а не глобальная настройка.
- Определение контура версионировано: расчёт доходности ссылается на версию, иначе изменение состава контура задним числом молча меняет исторические цифры.

### 4.11 Сшивание переводов

Две половины перевода приходят из разных источников с разными датами. Правило сопоставления: одинаковая сумма, встречное направление, близкие даты, разные счета. Сопоставление является вопросом классификации и обрабатывается вердиктом `needs_classification` (§10.4) с запоминанием ответа как правила. Неспаренные половины показываются отдельным списком и служат детектором пропущенных данных.

**Деньги в пути — отдельное состояние.** Списание первого числа и зачисление третьего без промежуточного состояния дают провал капитала второго числа и ложный убыток в TWR. Спаренный перевод создаёт позицию «в пути», входящую в стоимость портфеля.

### 4.12 Лоты: экономические и налоговые

**Экономический лот** — партия приобретения с датой, количеством, ценой, комиссией. Позиция является проекцией набора лотов.

**Налоговый лот** — проекция для целей налогообложения. Не совпадает с экономическим: у него своя область применения и свои правила переноса стоимости при корпоративных действиях и переводах.

**FIFO не является глобальной очередью по портфелю.** Область списания задаётся набором: налогоплательщик × налоговый агент × налоговая база × инструмент × счёт × налоговый режим счёта × год. Стратегия списания версионирована.

**FIFO не зашивается в факт продажи.** Событие `trade` хранит проданное количество и сумму. Какие именно лоты списаны — результат версионированной проекции. Исключение: если источник сообщает юридически значимое сопоставление лотов, оно записывается как факт.

Следствия наличия лотов:

- средняя цена, FIFO, LIFO — разные проекции одних лотов; отчёт показывает их рядом и объясняет расхождение между отображаемой средней ценой и налоговой базой;
- ЛДВ вычислим: три года владения — свойство лота, у позиции со средней ценой возраста нет;
- продажа части позиции показывает, какие лоты списаны и что осталось.

## 5. Оценка позиций

### 5.1 Две оценочные базы

Начисленный, но не выплаченный доход владельцу не принадлежит. Отсюда две стоимости, которые нельзя смешивать.

**`liquidation_value(date)` — «что я получу, закрыв всё сегодня».** Вклад расторгнут досрочно по условиям договора; бумаги проданы по доступному bid; вычтены комиссии и налог к уплате.

**`contractual_hold_value(date, horizon)` — «что будет, если ничего не делать».** Вклад дожит до конца срока по ставке договора, облигации до погашения, выплаты приходят по графику.

Разрыв между ними — цена досрочного выхода.

**Третьей базы (сглаженной «экономической NAV») не вводится.** Расчётные величины хранятся как атрибуты, а не как отдельная стоимость:

- `accrued_interest` — начислено с последней даты выплаты;
- `accrued_interest_payable_on_termination` — сколько из этого сохранится при расторжении сегодня;
- `next_posting_date` — ближайшая дата выплаты или капитализации.

**Обоснование отказа от третьей базы.** TWR телескопируется: при отсутствии внешних потоков произведение подпериодных доходностей равно `V_n / V_0 − 1`, поэтому форма траектории внутри периода на итог не влияет. Различие между ступенчатой и сглаженной кривой возникает только на неполной границе периода и ограничено сверху примерно `r/12` при ежемесячном начислении (при 20% годовых — до 1,67% стоимости вклада, в среднем около 0,83%). На годовом горизонте это до ~0,8 п.п. annualized, на пятилетнем — около 0,16 п.п. Влияние становится системным лишь в двух случаях: внешний поток пришёлся между начислением и выплатой, либо условия расторжения нелинейны. Оба случая обрабатываются флагом, а не отдельной базой.

### 5.2 Флаг граничного эффекта

Отчёт получает компактный маркер:

```
valuationTiming:
  crossesUnpostedAccrual: true
  unpostedAccrual: 8214 RUB
  includedInLiquidationValue: 0 RUB
```

Флаг показывается только при **одновременном** выполнении двух условий: граничный эффект ненулевой и материален (`unpostedAccrual > max(0.1% NAV, 100 RUB)`), **и** период обрывается между датами выплаты. Отдельно флаг выставляется, если внешний поток пришёлся внутрь такого интервала — там искажение системное (§5.1).

Само по себе «период начинается или заканчивается между выплатами» условием не является: почти любой произвольный период этому удовлетворяет, и маркер превратился бы в постоянный фон, который перестают замечать.

### 5.3 Асимметрия НКД и начисленных процентов

НКД по облигации обычно входит в расчётную сумму стандартной биржевой сделки — покупатель его оплачивает. Начисленные проценты по вкладу при досрочном расторжении, как правило, теряются полностью или частично. Облигация и вклад с одинаковой ставкой ведут себя по-разному, и разница именно в ликвидности накопленного дохода.

**Гарантией это не является.** Возможны отсутствие покупателя, дефолт, приостановка торгов, специальные режимы цены. Ликвидационная оценка использует доступный bid с учётом режима торгов и издержек; при отсутствии исполнимой цены значение помечается неполным, а не рассчитывается как гарантированное.

### 5.4 Политика оценки по классам активов

Единого правила нет, поэтому оно задаётся явно:

| Класс | Правило | Флаг качества |
|---|---|---|
| Ликвидная биржевая бумага | доступный bid; при отсутствии — previous close | возраст цены |
| Неликвидная биржевая бумага | previous close в пределах порога устаревания | `stale` при превышении |
| Нерабочий день | перенос последней цены (carry-forward) | `non_trading_day` |
| Вклад | функция условий договора на дату | — |
| Неликвид | последняя `valuation` в пределах срока действия | `stale` при истечении |
| Цены нет вовсе | значение неполное | `incomplete` |

Каждая оценка всегда возвращает флаг качества. Молчаливая подстановка запрещена; NAV на дату с неполными оценками помечается как неполный.

## 6. Доходность

### 6.1 XIRR — «сколько я заработал»

Денежные потоки, пересекающие границу контура, плюс текущая стоимость как терминальный поток.

Обязательные параметры расчёта, без которых результат не определён: **валюта отчёта**, **источник и тип курса** для каждой даты, **версия определения контура**. Дополнительно отчёт показывает доходность в локальных валютах и вклад валютной переоценки отдельно.

Реализация: Ньютон с откатом на бисекцию. При чередующихся знаках потоков уравнение может иметь несколько корней или ни одного — тогда возвращается явный отказ с объяснением, а не произвольное число.

### 6.2 TWR — «хороши ли были решения»

Строится по **ликвидационной** оценке (§5.1).

**Конвенция моментов оценки задаётся явно.** Точный TWR требует стоимости непосредственно перед внешним потоком и сразу после него. Один дневной NAV неоднозначен, если пополнение и движение рынка произошли в один день. При невозможности внутридневной оценки применяется **Modified Dietz** с явной маркировкой приближения.

### 6.3 Формальное тождество результата

Расчёт ведётся в валюте отчёта `R`.

```
NAV(t) = Cash(t) + MV(t) + Receivables(t) − Liabilities(t)
```

Обязательства включают признанный налог.

```
P = NAV(1) − NAV(0) − F_ext
```

где `F_ext` — внешние потоки (положительные при внесении, отрицательные при выводе).

Полное тождество:

```
P = RP_local + UP_local
  + RP_fx + UP_fx
  + Interaction
  + Income
  − Fees
  − TaxExpense
  + Other
```

- `RP_*` — реализованный результат, `UP_*` — нереализованный;
- `local` — изменение в валюте инструмента, переведённое по базовому курсу;
- `fx` — эффект курса при неизменной локальной величине;
- `Interaction` — перекрёстный член (см. §6.4);
- `Other` — включает `PriorPeriodTaxAdjustment` и прочие корректировки прошлых периодов.

### 6.4 Разложение валютного результата

Для интервала без транзакций, где `V` — стоимость в локальной валюте, `e` — курс:

```
e1·V1 − e0·V0 = e0·ΔV  +  V0·Δe  +  ΔV·Δe
                 local      fx      interaction
```

Это точное арифметическое тождество. **Перекрёстный член не прячется** ни в локальный, ни в валютный результат — он показывается отдельно. Причина: симметрия и независимость от условного порядка «сначала изменилась цена, потом курс».

Если представление требует ровно двух чисел, применяется симметричное разделение (Shapley):

```
local* = e0·ΔV + ½·ΔV·Δe
fx*    = V0·Δe + ½·ΔV·Δe
```

Ядро при этом обязано сохранять все три члена.

#### Алгоритм атрибуции по событийной шкале

Формула выше определена только для интервала без транзакций. Полное тождество содержит `RP_fx`, `UP_fx`, валютные `Income`, комиссии и налог, поэтому одной формулы недостаточно: одно и то же тождество допускает несколько несовместимых атрибуций, и проверка равенства `P` этого не обнаружит. Алгоритм фиксируется однозначно.

1. **Резка шкалы.** Временная ось режется на каждом `trade`, `income`, `fee`, налоговом событии, внешнем потоке и границе оценки.
2. **Открытый интервал.** Между точками резки количество постоянно — применяется трёхчленная формула выше.
3. **Момент сделки.** Отдельно фиксируются: `basis_released_local`; курс приобретения, по которому переводился basis; курс выбытия; реализованный локальный результат; реализованный валютный результат; реализованный перекрёстный член.
4. **Валютная выплата.** Сначала признаётся как `Income` по курсу даты признания, затем становится валютными деньгами; дальнейшее изменение курса относится к `UP_fx` по деньгам, а не к доходу.
5. **Комиссии и налоги** переводятся по курсу фактического признания, если не создают отдельного валютного обязательства.
6. **Прослеживаемость.** Каждый компонент несёт ссылку на событие или интервал, из которого получен. Без этого сумма невоспроизводима, а расхождение необъяснимо.

### 6.5 Частичная продажа, амортизация, налог другого периода

**Частичная продажа.**

```
RealisedLocal = GrossProceedsLocal − BasisReleasedLocal
B1 = B0 + BasisAdded − BasisReleased − BasisReturned
```

`BasisReleased` определяется проекцией списания лотов (§4.12). Нереализованный результат считается по интервалам между событиями; продажа закрывает накопленный нереализованный результат выбывшей части и переносит его в реализованный, не меняя общий итог.

**Амортизация номинала.** Амортизация уменьшает непогашенный номинал и выплачивает деньги; **количество бумаг не уменьшается**. У лота раздельно хранятся `quantity`, `nominal_per_unit`, `remaining_principal`.

```
Realised_amort = A − BasisReturned
```

При `A = BasisReturned` результат нулевой: это возврат собственного капитала, а не доход. Разница при ином соотношении является реализованным результатом по применимому правилу. Купон при этом остаётся `Income`.

**Налог, относящийся к другому периоду.**

```
TaxExpense = TaxRecognised + TaxEstimateRevision
```

Уплата или удержание ранее признанного налога уменьшает деньги и обязательство одинаково и на результат текущего периода не влияет.

Налог, удержанный в январе за прошлый год: в денежном потоке показывается январское удержание; в результате текущего года новым расходом он не является, если обязательство было признано на 31 декабря. Если не было признано — разница попадает в `PriorPeriodTaxAdjustment` внутри `Other`, но **не маскируется под налог на январский доход**. Возврат налога закрывает налоговое требование; неожиданный возврат является пересмотром оценки.

### 6.6 Числовая политика, округление и допустимая невязка

#### Три числовых режима

Требование «невязка равна нулю» невыполнимо без указания, в какой арифметике. `rust_decimal` имеет конечную точность, а деление и разнесение basis округляются внутри самой операции. Поэтому режимы разделяются явно.

| Режим | Где | Тип |
|---|---|---|
| **Точный** | тождество §6.3, разнесение basis, сверка, налоговая база | целые в минимальных единицах либо рациональные числа |
| **Денежный** | суммы, цены, курсы, НКД | `rust_decimal` с заданным масштабом |
| **Приближённый** | XIRR, `CAGR_0R`, DCF, ZCYC — то, что требует степеней, корней и итераций | явно заданная численная политика |

**Приближённые величины никогда не входят в денежное тождество.** Тождество §6.3 проверяет суммы, а не ставки. Ставка доходности является производной от сумм, а не их компонентом.

#### Политика для итерационных методов

Для каждого алгоритма фиксируются: точность, критерий остановки, максимум итераций, способ локализации корня и оценка погрешности. Всё это входит в результат рядом с числом.

Двоичная плавающая точка допустима **только** внутри решателей ставок и трансцендентных функций, с документированной границей погрешности. Она никогда не используется для проведённых сумм, налоговой базы и любого члена тождества. Запрет из §15.1 формулируется соответственно: `f64` запрещён в доменных величинах, а не во всём крейте без исключений.

#### Округление и распределение невязки

Промежуточные агрегаты не округляются. Проводки источников хранятся в опубликованной ими точности.

После однократного округления `K` компонентов и итога до минимальной единицы:

```
|round(P) − Σ round(C_i)| ≤ (K + 1) / 2 минимальных единиц
```

При десяти компонентах — не более 5 копеек. В представлении невязка принудительно распределяется методом наибольшего остатка, чтобы отображаемое тождество сходилось точно.

Тесты проверяют три условия:

```
невязка тождества в точном режиме == 0
невязка представления до распределения <= floor((K + 1) / 2) минимальных единиц
невязка представления после распределения == 0
```

**Важно:** если источник сам округлял каждую из `N` операций, его опубликованные суммы являются фактами. Оценивать допустимую ошибку как `N/2` копеек в этом случае нельзя.

## 7. Облигации

### 7.1 Доходность без допущения о реинвестировании

Единственной цифры «сколько я получу» не существует: 100 рублей завтра и через три года — разные результаты. Но можно дать одну метрику при одном прозрачном допущении — **все промежуточные выплаты хранятся деньгами под 0%**.

**Годовая доходность удержания без реинвестирования** (zero-reinvestment holding-period CAGR):

```
C0  = полная стоимость приобретения (dirty price + комиссия)
CF_i = будущие выплаты после прогнозных налогов и расходов
T   = число дней до окончательного погашения

W_T      = Σ CF_i
Profit   = W_T − C0
HPR      = W_T / C0 − 1
CAGR_0R  = (W_T / C0) ^ (365 / T) − 1
```

Это не YTM: даты промежуточных выплат на `CAGR_0R` не влияют, поскольку доходность хранящихся денег явно принята нулевой. Допущение отображается рядом с цифрой.

**Минимальный честный набор для владельца:**

1. **График чистых выплат** — сколько и когда придёт.
2. **Чистый денежный излишек** `W_T − C0` — сколько рублей будет заработано номинально.
3. **HPR без реинвестирования** — прибыль относительно вложенного за весь срок.
4. **CAGR без реинвестирования** — сопоставимая годовая цифра.
5. **YTM / чистый IRR** — стандартная характеристика самих потоков, с пояснением, что реализованная сложная доходность потребует реинвестирования.

Если владелец тратит купоны, а не хранит их, единой цифры терминального капитала не существует — остаются график выплат и IRR. Поэтому допущение всегда показывается явно.

### 7.2 Специфика инструментов

**НКД** учитывается явно: при покупке входит в затраты, при продаже — в доход.

**Амортизация** — см. §6.5.

**Флоатеры.** Купонная формула хранится как версионированная спецификация: дата фиксинга, референсный индекс, лаг наблюдения, спред, floor/cap, база начисления дней, календарь публикации, правило fallback. Зафиксированные ставки — отдельные факты с указанием источника. Бывают также step-up и call-linked формулы.

**Оферта** — см. §4.7: право, а не автоматическое действие.

**Замещающие облигации и валютный номинал.** Раздельно хранятся `denomination currency` (валюта обязательства), `settlement currency` (валюта расчётов), `quote currency` (валюта котировки), `reporting currency` (валюта отчёта), плюс формула пересчёта. При замещении фиксируется происхождение инструмента (lineage) и перенос затрат и сроков владения.

## 8. Вклады

### 8.1 Договор — факт, начисление — проекция

Расчётное начисление не является внешней операцией: оно вычисляется нами, отменяется при досрочном расторжении и пересчитывается при изменении условий. Записывать его как факт означало бы наполнить «неизменяемый журнал» синтетикой, которую придётся массово править.

Фактами являются:

- `deposit_contract` и его версии (изменение ставки, пополнение, частичное снятие, пролонгация);
- фактическая **выплата** процентов;
- фактическая **капитализация**;
- закрытие вклада, в том числе досрочное.

Начисление между этими фактами строится проекцией из условий договора.

### 8.2 Параметры договора

Начисление, выплата и капитализация — три независимых параметра.

| Параметр | Варианты |
|---|---|
| Периодичность начисления | ежедневно · ежемесячно · ежеквартально · в конце срока |
| Правило даты | последний день месяца · дата открытия |
| База начисления дней | фактическая/365 · фактическая/366 · иная |
| Капитализация | да (в тело) · нет (выплата) |
| Направление выплаты | счёт вклада · карта/брокерский · в конце срока |
| Ставка | фиксированная · лестница по периодам · плавающая от ключевой |
| Пополнение | запрещено · разрешено · с ограничениями |
| Снятие | запрещено · до неснижаемого остатка |
| Досрочное расторжение | до востребования · льготное · с потерей процентов |

Условия расторжения дают величину, отсутствующую в существующих сервисах: сколько владелец реально получит, забрав вклад сегодня.

### 8.3 Сверка проекции с фактом

Банк начисляет по своей базе дней и своему округлению. Корректная проекция нередко совпадёт с фактом точно, но расхождение возможно и должно обрабатываться штатно, а не как сбой.

**Правила:**

1. Фактическая выплата или капитализация — безусловный факт.
2. Проекция **никогда** не подгоняется молчаливой балансирующей поправкой.
3. Расхождение является в первую очередь диагностикой модели договора.
4. По итогам разбора: либо причина найдена и создаётся новая версия условий, либо причина не установлена и расхождение сохраняется как необъяснённая ошибка прогноза.

**Версия условий имеет интервал действия.** Новая версия, созданная после разбора расхождения, применяется с даты, подтверждённой свидетельством, и не переписывает прошлое задним числом без него. Иначе разбор одного расхождения молча изменит все предыдущие периоды.

```
InterestReconciliation {
  period
  projectedGross
  actualGross
  difference
  status: matched | explained_by_contract_revision
        | explained_by_bank_rounding | unexplained
  ruleVersion
  evidence
}
```

Порог автоматического признания разницы округлением выводится из алгоритма, а не задаётся универсальными «несколькими копейками»:

```
tolerance ≤ (число точек округления) × 0.5 минимальной единицы
```

Ежедневное округление банком даёт иной предел, чем однократное в конце месяца.

### 8.4 Как это входит в тождество

В историческом результате участвует **только фактическая величина**:

```
Income = ActualGrossInterest
```

Ошибка прогноза живёт в отдельном отчёте качества прогноза:

```
ActualGrossInterest = ProjectedGrossInterest + ForecastVariance
```

**Эти два разложения нельзя складывать** — получится двойной счёт. Если банк корректирует ранее выплаченный процент отдельной проводкой, это новый факт корректировки дохода со ссылкой на исходный период, а не изменение старого события.

## 9. Налоги

### 9.1 Модель

Гибрид: фактически удержанный налог — истина о прошлом; расчётный налог на нереализованную прибыль — оценка. Расхождение отображается и служит самопроверкой движка.

Правила версионированы по годам. Налоговое правило — чистая функция от подготовленного `TaxContext` (§3.2), привязанная к году. Изменение закона добавляет версию; история пересчитывается по правилам своих лет.

### 9.2 Налоговых баз несколько

Доход сначала **классифицируется в конкретную налоговую базу**, и только затем применяются правила внутри неё. Единой функции `tax(сумма, год)` не существует.

Разные базы имеют разные правила сальдирования и разные ставки. **Дивиденды нельзя уменьшить убытком от продажи акций.** Раздельно рассматриваются как минимум: дивиденды; операции с обращающимися ценными бумагами; операции с необращающимися; проценты по вкладам и остаткам на счетах; прочие доходы.

Правило является функцией не только суммы и года, но и: резидентства, типа дохода, обращаемости инструмента, налогового агента, режима счёта, применимых вычетов и ранее перенесённых убытков.

### 9.3 Проценты по вкладам

Это **не** расходуемый по банкам лимит остатка. База определяется по совокупности полученных за год процентов с установленными исключениями; необлагаемая сумма рассчитывается по формуле с ключевой ставкой, применимой к данному году. Налог, как правило, рассчитывает ФНС по сведениям банков, а не удерживает каждый банк.

Моделируется агрегатор процентных доходов налогоплательщика за год: дата фактического получения, валюта и курс, исключаемые счета, годовая формула, признак наличия доходов вне наблюдаемого системой контура. Отчёт показывает **сценарную оценку базы при известных системе данных**, а не «остаток лимита».

### 9.4 Режим счёта

ИИС не является одним флагом. Вводится версионированный `account_tax_regime` с датами действия, типом договора, историей применённых вычетов, закрытиями, трансформациями и подтверждающими документами. Различаются старые договоры с вычетами типов А и Б и последующие режимы; учитываются минимальные сроки, ограничения на количество договоров и восстановление налога при досрочном закрытии.

### 9.5 Валютная переоценка

Разделяются **экономическая FX-атрибуция** (компонент результата портфеля, §6.4) и **налогооблагаемые валютные события**. Нереализованная рублёвая переоценка не является автоматически налоговой базой. Классификация объекта обязательна: валюта, валютная ценная бумага, цифровая валюта, металлический счёт, физическое золото — правила различаются.

### 9.6 Обязательные ограничения

- Каждая сумма **прослеживается до конкретного правила** с указанием нормы и года: не «налог 12 400», а «12 400 = (доход 95 385 − затраты 0) × 13%, правило „проценты по купонам, 2021+“».
- Расчётный налог всегда помечен как **оценка** и сверяется с фактически удержанным.
- Модуль правил оптимизируется под читаемость и проверку глазами, а не под производительность.
- При недостатке данных возвращается диапазон или `not_computable`, а не точная цифра на выдуманных входных данных.
- Система готовит данные, но **не подменяет декларацию и не даёт налоговых советов**. Разработчик не является налоговым консультантом; законодательство меняется и содержит спорные трактовки. Налоговые формулировки требуют проверки по редакции НК РФ, действующей для конкретного периода.

### 9.7 Планирование

Даты наступления ЛДВ по лотам; сценарная оценка базы по процентным доходам; объём убытка, доступного к фиксации для сальдирования **внутри соответствующей базы**. С явной оговоркой, что это арифметика, а не рекомендация.

## 10. Приёмка данных

### 10.1 Единый вход и построчный разбор

Все источники сводятся к общему формату. Импортная пачка разбирается **построчно**, и каждая строка получает собственный статус. Документ целиком не отклоняется из-за одной непонятой строки.

| Источник | Устройство | Хрупкость |
|---|---|---|
| API брокера | адаптер на брокера, периодическая синхронизация, шифрованный токен | средняя |
| Отчёты брокера | парсер на связку брокер+формат; версия парсера пишется в provenance для повторного разбора | высокая |
| Внешний агент | нормализованные операции через REST | зависит от агента |
| Руки / CSV | формы, загрузка файла | низкая |

### 10.2 Почему не ручное подтверждение операций

Подтверждение каждой операции человеком отвергнуто как проектное решение: оно перекладывает на человека работу, с которой справляется арифметика, и на практике вырождается в нажатие «ок» не глядя — что хуже отсутствия проверки.

Вместо этого достоверность устанавливается сверкой, а человек отвечает только на вопросы классификации, которые из арифметики не выводятся.

### 10.3 Многомерная сверка и уровни достоверности

**Статус присваивается не операции, а утверждению о полноте счёта на интервале по измерению.**

```
ReconciliationStatus {
  accountId
  from, to
  dimensions: {
    cash:       accepted_independent | accepted_internal | provisional | discrepant
    positions:  ...
    taxBasis:   ...
    income:     ...
  }
  evidence[]
}
```

Три уровня: `provisional` → `accepted_internal` → `accepted_independent`.

**Почему трёх уровней, а не двух.** Операции и контрольные остатки извлекаются одним парсером из одного документа. Общая ошибка парсера исказит обе стороны проверки одинаково, и сверка её не заметит. Утверждение «ошибка, сохраняющая и остаток, и количества, практически невозможна» неверно: не ловятся компенсирующие пропуски, перепутанные даты внутри интервала, парные buy+sell, неверное разнесение комиссии и НКД при верной итоговой сумме, неверная цена при верных количестве и сумме, обмен одинаковых количеств между близкими инструментами, неверная валюта с компенсирующим курсом.

**Основания автоматического повышения статуса** (участие человека не требуется):

| # | Основание | Даёт уровень | Условие |
|---|---|---|---|
| 1 | Начальный остаток следующего отчёта совпадает с вычисленным остатком предыдущего периода | **internal** | тот же брокер, тот же парсер — общая ошибка разбора исказит обе стороны |
| 2 | Конечный остаток одного отчёта совпадает с начальным следующего (непрерывность) | internal | — |
| 3 | API брокера совпадает с разобранным отчётом по деньгам и позициям | independent | другой канал получения и другой код разбора |
| 4 | Депозитарный отчёт подтверждает количества и custody | independent (только позиции) | другой источник |
| 5 | Раздельные контрольные секции одного документа сходятся одновременно: остатки, обороты Dt/Kt, количества, сумма комиссий, сумма купонов и дивидендов, удержанный налог | internal | независимые уравнения, но один документ и один парсер |
| 6 | Фактическая выплата или закрытие вклада подтверждает график предшествующего периода | internal, **independent** если факт получен другим каналом | выписка банка против нашей проекции — независимо; та же выписка, что дала условия, — нет |
| 7 | Количества после корпоративного действия совпадают с параметрами выпуска и следующим остатком | independent | параметры выпуска получены из внешнего источника (MOEX), а не из отчёта |
| 8 | Справка налогового агента подтверждает агрегированные доходы и удержанный налог | independent (только агрегаты) | отдельный документ, отдельный парсер |

**Уровень `independent` присваивается только при выполнении условия независимости источника**, а не по типу основания. Ключевой критерий: подтверждающие данные не должны проходить через тот же код разбора и тот же документ, что и подтверждаемые. Следующий отчёт того же брокера, разобранный тем же парсером, — это непрерывность, а не независимость.

Подтверждённый остаток принимает интервал по измерениям `cash` и `positions`, **не подтверждая** при этом классификацию и налоговую стоимость. Ручная операция не становится `accepted` от течения времени.

### 10.4 Вердикты приёмки

Отдельного шага подтверждения в нормальном пути нет — есть отправка и вердикт.

| Вердикт | Значение | Действие |
|---|---|---|
| `accepted` | записано, сверка сошлась | никакого |
| `provisional` | записано, независимого подтверждения пока нет | никакого, статус повысится сам |
| `discrepancy` | не сходится: сумма, счёт, интервал, измерение, кандидаты | владелец разбирается |
| `needs_reconciliation` | сверить не с чем — требуется остаток | владелец называет цифру |
| `needs_classification` | неоднозначная классификация | владелец отвечает один раз, ответ становится правилом |
| `unsupported` | операция вне периметра (§11) | денежный эффект сохранён, экономика не достраивается |

Правила классификации («переводы со счёта A на счёт B всегда внутренние») видимы и редактируемы; исправление правила пересчитывает историю.

**Ограничение `needs_reconciliation`.** Названный владельцем текущий остаток подтверждает только снимок: он ничего не говорит о себестоимости, доходах, оборотах и датах. Поэтому он повышает статус измерений `cash` и `positions` на соответствующем интервале и **не трогает** `taxBasis` и `income`.

### 10.5 Блок качества данных

Записи без второго источника **считаются в отчётах по умолчанию** — иначе система бесполезна именно для банков без экспорта и ручного ввода. Дисклеймер у каждой строки не нужен; API возвращает один компактный блок:

```json
{
  "dataQuality": {
    "status": "mixed",
    "navCoverage": {
      "acceptedIndependent": 0.72,
      "acceptedInternal": 0.18,
      "provisional": 0.10
    },
    "materialIssues": [
      { "accountId": "deposit-1",
        "period": "2026-01-01/2026-08-22",
        "reason": "no independent balance source" }
    ]
  }
}
```

В обычном представлении достаточно строки вида `mixed · 90% reconciled`. Отдельное предупреждение обязательно только тогда, когда `provisional`-данные материально влияют на ответ или делают его невычислимым.

### 10.6 Идемпотентность и дедупликация

Иерархия ключей, от сильного к слабому:

1. **Стабильный `sourceOperationId`** — если источник его даёт.
2. **Клиентский `idempotencyKey`** — повтор вызова возвращает тот же результат.
3. **Отпечаток нормализованной сырой записи.**
4. **Хеш документа + локатор строки.**
5. **Вероятностная оценка дубликата** — показывается, но **не приводит к автоматическому удалению**.

Естественный ключ вида «счёт + дата + сумма» слишком слаб: он даёт ложные совпадения и не ловит дубликаты после нормализации. Две одинаковые покупки в один день — законная ситуация.

### 10.7 Частичная история

У каждого счёта — дата начала учёта. Где история есть, расчёт идёт с первого дня; где нет — восстановленное начало.

**`opening_position` является набором утверждений с provenance и уровнем уверенности**, а не строкой с ценой:

```
quantity:            known | estimated
acquisitionDate:     known | estimated | unknown
taxBasis:            documented | estimated | unknown
basisCurrency + rate
feesIncluded:        yes | no | unknown
ldvEligibility:      known | unknown
priorCorporateActions: known | unknown
```

Если налоговая стоимость неизвестна, налоговый отчёт возвращает диапазон или `not_computable` — но не точную цифру.

**Отчёт обязан сообщать о неполноте:** «XIRR посчитан с 01.03.2024, ранее данных нет», «счёт X учтён восстановленным началом». Неполнота не является ошибкой; ошибкой является её сокрытие.

## 11. Периметр: шорты, маржа, РЕПО

Шорты, маржинальная торговля, РЕПО и ПФИ **вне периметра**. Ledger обязательств не строится.

Граница является **возможностной, а не документной**: встретив неподдерживаемую строку, система не отклоняет весь отчёт.

**Проценты по марже.** Если сумма сообщена однозначно: импортируется денежное списание как `fee` с `origin = margin_interest`; период помечается `unsupportedFinancingPresent`; эффективная ставка и маржинальное обязательство не рассчитываются. Денежное разложение сходится, аналитика ограничена фактически списанной суммой.

**Брокерское РЕПО овернайт.** Превращать в продажу и обратную покупку запрещено — это исказит лоты, срок владения и налоги. Исходные строки уходят в карантин; независимые комиссии и проценты импортируются, если их денежный смысл однозначен; движения бумаг по РЕПО к инвестиционным лотам не применяются; сверка количеств на соответствующие даты получает исключение `unsupported_repo_encumbrance`, а не расхождение, которое владелец должен «чинить»; остальные строки импортируются.

**Отрицательный денежный остаток поддерживается** даже в long-only системе — он возникает из-за таймингов расчётов, комиссий и технического овердрафта.

| Ситуация | Классификация | Последствия |
|---|---|---|
| Закрывается известным расчётом в допустимый срок | `temporary_settlement_deficit` | расчёты разрешены |
| Присутствуют проценты по марже или признак кредита | `unsupported_margin_liability` | см. ниже |
| Причина неизвестна | `unclassified_negative_cash` | см. ниже |

В двух последних случаях: отрицательные деньги входят в NAV как обязательство; XIRR по наблюдаемым потокам считается; ликвидационная стоимость и результат помечаются неполными, если неизвестны начисленные проценты или стоимость закрытия; налоговые и финансовые отчёты за период возвращают `not_computable`; **остальные счета и периоды продолжают считаться**.

Система сохраняет наблюдаемый денежный эффект и не теряет остальной отчёт, но отказывается выдумывать экономику неподдерживаемого финансирования.

## 12. Рыночные данные

| Что | Источник | Назначение |
|---|---|---|
| Котировки, параметры выпусков, купоны, амортизация | MOEX ISS | оценка, график выплат |

**История цен хранится, а не только кэшируется.** TWR требует ежедневного ряда за весь период; цену за прошлую дату получить задним числом трудно, дорого или невозможно. Кэш с TTL — для свежих данных, хранилище истории — постоянное. Курс, использованный в расчёте, сохраняется вместе с источником и датой (входит в `TaxContext`).

## 13. API и интеграция с агентом

- **REST + OpenAPI-спека.** Веб-UI будет ходить в тот же API, что и агент.
- **API возвращает готовые отчёты, а не сырые данные.** `/reports/returns`, `/reports/allocation`, `/reports/tax` отдают финальные числа, посчитанные движком, с периодом, применёнными правилами и блоком `dataQuality`.
- **Агенту запрещена собственная арифметика.** Требование проверяемо: число в ответе агента, отсутствующее в ответах API, является ошибкой.
- **Агентский токен не пишет в журнал напрямую.** Запись — результат прохождения приёмки, а не отдельное разрешённое действие.
- Ошибки валидации — `422` с указанием поля, ожидаемого и полученного значения.
- **Скилл** для агента описывает семантику: контуры, приёмка, вердикты, ключи идемпотентности, запрет на вычисления, трактовка `dataQuality` и `not_computable`.

**MCP не реализуется.** Любой харнесс умеет HTTP; MCP добавил бы второй транспорт, вторую аутентификацию и второй набор описаний инструментов, требующий синхронизации. Остаётся как возможная тонкая обёртка над готовым API.

## 14. Безопасность и сохранность

- **Аутентификация с первого дня.** Отложенная аутентификация не добавляется никогда.
- **Токены брокерских API шифруются на диске** ключом вне базы. Утечка файла БД не должна давать доступ к брокерскому счёту.
- **Только read-only доступ к брокеру**, где брокер это различает. Торговые права не запрашиваются никогда.
- **Агентские токены отдельные, отзываемые, с журналом использования.**
- **Секреты не попадают в логи.** Логирование обязательно (без него отладка парсеров невозможна) с вычищением чувствительных полей.
- **HTTPS** через реверс-прокси, документируется в инструкции по развёртыванию.
- **Rate limiting** на API.

**Архивный бандл вместо голого экспорта.** Экспорт одних событий не является полным бэкапом: из него получатся другие проекции. Версионированный бандл включает: события, справочник инструментов, счета и контуры (с версиями), правила классификации, договоры вкладов, provenance источников, использованные рыночные данные и курсы, `TaxContext`, схему и контрольные суммы. Снимок SQLite и переносимый архив — разные механизмы, нужны оба.

## 15. Проверяемость

Цена ошибки в этой системе высока, а разработка ведётся агентом. Поэтому проверка строится слоями — каждый ловит свой класс ошибок, и ни один не заменяет остальные.

### 15.1 Слой 1 — типы, делающие ошибку непредставимой

Самый дешёвый слой: ошибка не ловится тестом, а не существует.

- `Money<Rub>` и `Money<Usd>` не складываются.
- `PostedMinor` (проведённые суммы) и `CalcDecimal` (расчётные величины) не смешиваются.
- Шесть семантических дат (§4.2) — шесть разных типов: `TradeDate`, `SettledDate`, `CashPostedDate`, `EntitlementDate`, `PaidDate`, `TaxPeriod`. Передать одну вместо другой невозможно. Без этого их гарантированно перепутают.
- `Option<T>` для всего, что может быть неизвестным (§4.9). Нулевая заглушка не компилируется.
- Enum-ы с данными для семейства событий и корпоративных действий — новая ветка ломает сборку везде, где её не обработали. Строковые дискриминаторы запрещены там, где возможен enum.
- **`f64` запрещён в доменных величинах** — проведённых суммах, налоговой базе, компонентах тождества. Внутри решателей ставок и трансцендентных функций допустим с документированной границей погрешности (§6.6). Проверяется линтом в CI.
- `#![forbid(unsafe_code)]` **во всех крейтах первой стороны**. Это не гарантирует отсутствия `unsafe` в программе: зависимости (`rusqlite`, TLS, системные библиотеки) его используют. Для них — фиксация lockfile, `cargo deny`/`cargo audit`, минимизация features и проверка обновлений. Обещать сборку без transitive unsafe нельзя.
- Ограничение на число параметров типа у публичного типа (§3.2) и лимиты цикломатической сложности.
- `Mutex` и async запрещены в `iaam-core` архитектурным тестом.

### 15.2 Слой 2 — инварианты как исполняемый код

Каждая проекция возвращает результат вместе с проверенными инвариантами:

- тождество §6.3 в точном режиме равно нулю;
- сумма лотов равна позиции;
- ноги события сходятся в ноль;
- трёхчленное валютное разложение равно прямой разности `e1·V1 − e0·V0`;
- невязка представления укладывается в границу §6.6.

**Нарушение инварианта — не то же самое, что неполные данные.**

| Ситуация | Поведение |
|---|---|
| Входные данные неполны | нормальный результат плюс `dataQuality` (§10.5) |
| Нарушен внутренний инвариант | **типизированная внутренняя ошибка**, отчёт не выдаётся, расчёт логируется с идентификатором корреляции |

Возвращать число с предупреждением после доказанного нарушения тождества нельзя: `dataQuality` предназначен для неполноты входа, и владелец воспримет такой результат как «просто менее достоверный». При пакетном расчёте остальные независимые счета продолжают считаться, а повреждённый результат возвращается как `not_computable`.

**Инварианты нельзя ослаблять.** Отключение или смягчение проверки — изменение, требующее явного обоснования, а не способ починить сборку.

### 15.3 Слой 3 — свойства (`proptest`)

Свойство без указания области применимости — источник ложных падений, на которые агент отвечает ослаблением генератора до тавтологии. Поэтому область задаётся для каждого.

| Свойство | Область применимости |
|---|---|
| `P&L[a,c] = P&L[a,b] + P&L[b,c]` | **только аддитивные величины**, при согласованной оценке на границе `b` и одинаковой политике признания |
| `1 + TWR[a,c] = (1 + TWR[a,b]) · (1 + TWR[b,c])` | при корректной оценке на границе и правильном отнесении внешнего потока к одной из сторон |
| XIRR: подстановка найденного корня в NPV даёт ноль в пределах заявленной точности | **свойства склейки у XIRR нет** — IRR не цепляется |
| XIRR инвариантен к умножению всех потоков на `k > 0` | масштабная инвариантность, налоги и комиссии исключены |
| Перестановка порядка импорта не меняет проекцию | всегда (§4.8) |
| Повторный импорт не меняет состояние | всегда (§10.6) |
| Событие вместе со своим сторно оставляют состояние нетронутым | всегда |
| Нейтральное событие ничего не меняет | **все** ноги, количества, номинал и метаданные нулевые — не только денежная сумма |
| Налоги: монотонность по доходу | только внутри одного участка шкалы и одной налоговой базы |
| Сдвиг всех дат на равное число дней | только в искусственном календаре без налоговых правил, без високосности, без календаря выплат |
| Переименование инструмента ничего не меняет | только отображаемое имя, **не** идентичность инструмента и не его классификация |

Свойства, которые я ранее записал без оговорок и которые **неверны в общем виде**: склейка периодов для XIRR; умножение всех сумм на `k` при наличии прогрессивной шкалы, порогов, минимальных комиссий и необлагаемых сумм; сдвиг дат при наличии налоговых лет, ЛДВ и базы начисления дней; «нулевая сумма — нет эффекта» при сплите и переводе бумаг, у которых денежный итог нулевой, а последствия реальны.

### 15.4 Слой 4 — независимые эталоны

Проверка «два способа дают одно и то же» имеет силу **только если способы действительно независимы**. Если они делят код или один вычисляется как остаток другого, тест сходится всегда и не проверяет ничего.

**Пары, которые вырождаются в тавтологию и потому отвергнуты:**

| Отвергнутая пара | Почему не работает |
|---|---|
| Реализованный результат: по лотам против тождества | если реализованный вычисляется как остаток тождества, сходимость гарантирована |
| NAV: сумма позиций против переигрывания потоков | денежные потоки не восстанавливают рыночную стоимость; способ B неизбежно подмешает те же цены |
| Начисление против фактической выплаты | это сверка с допуском (§8.3), а не проверка равенства |
| FX: три члена против прямой разности | точное алгебраическое тождество над теми же входами — это инвариант (§15.2), а не эталон |
| FIFO против количества у брокера | количество не подтверждает, **какие** лоты списаны: любой порядок даёт то же количество |

**Настоящие эталоны:**

| Величина | Эталон |
|---|---|
| Реализованный результат | отдельная маленькая эталонная реализация на рациональной арифметике, написанная **другим алгоритмом** |
| NAV | позиционный NAV против баланса, где каждая операция проведена независимыми бухгалтерскими ногами |
| Проценты по вкладу | замкнутая формула для фиксированной ставки без округления, плюс фикстуры под конкретные банковские правила |
| Валютная атрибуция | заранее рассчитанные валютные сценарии с независимо замороженными входами |
| Списание лотов | сравнение не количества, а **released basis, оставшихся дат приобретения и налоговой стоимости** — со справкой или детализацией налогового агента |

**Эталонный код живёт в отдельном крейте и не зависит от production-проекций.** Общие функции между production и эталоном запрещены ниже уровня примитивов Decimal и дат. Иначе общая ошибка проявится в обоих.

### 15.5 Слой 5 — эталоны против реальности

Реальные брокерские отчёты владельца как источник истины. Ожидаемые значения считаются **независимо** — вручную или сверкой с отчётом. Тест, где ожидаемое значение взято из вывода самой программы, закрепляет ошибку.

### 15.6 Слой 6 — метаморфные тесты

Применяются с теми же оговорками об области, что и в §15.3. Безопасные преобразования:

- добавили счёт вне контура → доходность контура не изменилась (§4.10);
- переставили независимые счета местами → результат по каждому не изменился;
- разделили один инструмент на два идентичных с половинными количествами → агрегаты не изменились;
- умножили все денежные потоки на `k` при отключённых налогах, порогах и минимальных комиссиях → линейные величины умножились на `k`, доходности не изменились.

### 15.7 Риски агентской разработки

Разработку ведёт агент, который пишет **и код, и тесты**. Тест, проходящий впустую, выглядит неотличимо от рабочего. Это не гипотетический риск, а нормальный режим отказа.

**Режимы отказа, которые механически проходят обычную зелёную сборку:**

- тест и код разделяют одну ошибочную вспомогательную функцию;
- сложный модуль исключён из области мутационного тестирования;
- выжившие мутанты объявлены эквивалентными без доказательства;
- тесты запускаются не со всеми feature-флагами;
- снапшоты обновлены массово;
- новый код недостижим и потому «не имеет ошибок»;
- мок повторяет ошибку реального адаптера;
- ошибка проявляется только при другой временнóй зоне, локали, разрядности или при конкурентном выполнении;
- проверка «починена» добавлением `allow`, `ignore`, широкого допуска или ветки `_ =>`;
- `forbid(unsafe_code)` не распространяется на зависимости.

**Механические заслоны в CI** (не «человек должен внимательно ревьюить»):

| Заслон | Что закрывает |
|---|---|
| `cargo test --workspace --all-features` | тесты не со всеми features |
| `cargo hack test --feature-powerset` для критичных крейт | комбинации features |
| `cargo nextest` плюс отдельный последовательный прогон stateful-тестов | конкурентные эффекты |
| `cargo clippy --workspace --all-targets --all-features -- -D warnings` | деградация качества |
| diff-lint: запрет новых `allow`, `expect`, `ignore`, `todo!`, `unimplemented!`, `_ =>` в критичных enum | ослабление проверок |
| Порог выживаемости мутантов **по каждому критичному модулю**, а не общий | исключение модуля из области |
| Манифест контрольных сумм замороженных фикстур; изменение требует отдельного авторизованного флага | подгонка эталона под баг |
| Эталонный крейт без зависимости на production-проекции | общий код между тестом и кодом |
| `cargo llvm-cov` с покрытием по диффу и по ветвям | недостижимый новый код |
| `cargo deny` / `cargo audit`, проверка lockfile | цепочка зависимостей |
| Тест направления зависимостей через `cargo metadata` | нарушение графа §3.2 |
| Детерминированный повтор с несколькими seed, timezone и locale | зависимость от окружения |
| Запрет автоматического `insta accept` в CI | массовое обновление снапшотов |
| Проверка, что замороженные фикстуры действительно читаются тестами | мёртвые эталоны |

**Замороженные эталоны.** Ожидаемые значения золотых сценариев приходят из независимого источника и помечены как неизменяемые. **Агенту запрещено приводить падающий тест в соответствие с кодом правкой ожидаемого значения.** Изменение эталона требует решения владельца.

### 15.8 Остальное

- **Налоговые правила** тестируются по годам и по базам отдельно.
- **Контрактные тесты API** против OpenAPI-спеки, порождённой из типов (`utoipa`).
- **Снапшоты отчётов** (`insta`) ловят непреднамеренные изменения вывода.
- **Внешние источники замоканы**; живые вызовы — отдельным набором, запускаемым вручную.

### 15.9 Золотые сценарии

Обязательный набор, фиксируется до заморозки схемы:

| Сценарий | Что проверяет |
|---|---|
| Облигация с амортизацией | возврат principal не является доходом |
| Вклад с капитализацией и досрочным расторжением | две оценочные базы, потеря начисленного |
| Продажа части позиции | basis released, перенос нереализованного в реализованный |
| Лот, доживший до ЛДВ | возраст лота, налоговая проекция |
| Перевод бумаг между брокерами | сохранение налоговой стоимости и даты приобретения |
| Доудержанный в январе налог за прошлый год | обязательство в NAV, `PriorPeriodTaxAdjustment` |
| Возврат излишне удержанного налога | закрытие налогового требования |
| Дивиденд в валюте | FX-разложение на три члена |
| Замещающая облигация | lineage, валюта номинала против валюты расчётов |
| Оферта без предъявления | бумага не гасится автоматически |
| Сплит с дробным остатком | денежная компенсация, перенос basis |
| Делистинг | оценка при отсутствии рынка |
| Частичная история без налоговой стоимости | `not_computable` вместо выдуманной цифры |
| Отрицательный денежный остаток | классификация, обязательство в NAV |
| Две одинаковые сделки в один день | дедупликация не срабатывает ложно |
| Компенсирующая ошибка парсера | сверка из одного документа даёт только `accepted_internal` |
| Перевод между счетами внутри контура | XIRR не меняется |

## 16. Этапы поставки

Главный вывод ревью: этап 1 нельзя проектировать вокруг long-only лотов, одной даты события и XIRR — иначе поздние этапы потребуют миграции журнала фактов, объявленного неизменяемым фундаментом.

Поэтому этапы делятся не по объёму функций, а по **необратимости**.

### 16.1 Необратимое ядро — обязано быть в схеме с первого коммита

Отсутствие любого пункта заставит менять смысл уже записанных фактов.

1. Версионированный envelope события (§4.1)
2. Несколько семантических дат — заполнять не обязательно, допускать обязательно (§4.2)
3. Сохранение сырых значений без потери информации (§4.4)
4. Раздельные идентичности owner / account / custody / instrument / source (§4.5)
5. Типизированные ноги движения (§4.3)
6. Разделение проведённых сумм и расчётных величин, политика округления (§3.4)
7. Append-only семантика исправлений с детерминированным разрешением конфликтов (§4.8)
8. Provenance: хеш сырья, ID операции источника, версия парсера, документ и локатор строки (§4.1)
9. **FIFO не зашит в факт продажи** — списание лотов является версионированной проекцией (§4.12)
10. `unknown` как полноценное значение (§4.9)

Это требования к **схеме и дисциплине записи**, а не к объёму вычислений. Они не превращают первый этап в налоговый движок.

### 16.2 Аддитивное — добавляется без миграции фактов

Налоговые лоты и классификация в базы; ЛДВ, ИИС, сальдирование; NAV и TWR; формальное разложение результата; бенчмарки; расчёт начислений по вкладам; сценарии ставок; новые типы корпоративных действий (если исходные события не теряют данные); история рыночных данных; налоговые обязательства как проекция и последующие события; отдельная модель чтения для реализованного и нереализованного результата.

**Критерий:** первый этап обязан сохранить достаточные факты, но не обязан уметь строить все будущие проекции.

### 16.3 Последовательность

| Этап | Содержание | Отвечает на вопрос |
|---|---|---|
| 1 | необратимое ядро (§16.1), ручной ввод и CSV через API, лоты, позиции, денежные потоки, **XIRR до налога** | «сколько внесено и сколько заработано до налога» по счёту |
| 2 | построчный импорт отчётов, многомерная сверка, уровни достоверности, правила классификации, `dataQuality` | «цифрам можно верить — вот на сколько именно» |
| 3 | облигации и вклады целиком (НКД, амортизация, флоатеры, договоры и начисления), MOEX и ЦБ, метрики §7.1 | «сколько придёт и когда» |
| 4 | налоговые базы, налоговые лоты, ЛДВ, ИИС, тождество результата §6.3 | «сколько заработано после налога и из чего сложилось» |
| 5 | ряд NAV, TWR, бенчмарки, сравнение альтернатив | «был ли LQDT правильным решением» |
| 6 | API брокеров, налоговое планирование | «что сделать до конца года» |
| 7 | веб-UI | ежедневный взгляд без агента |

**Честная формулировка результата этапа 1:** денежные потоки и предварительный XIRR **до налога** для простых long-only бумаг. Обещать «сколько я заработал» в полном смысле на этапе 1 нельзя — налоги появляются на этапе 4.

## 17. Технологический стек

**Язык: Rust.**

Выбор сделан по двум требованиям спеки, которые прямо попадают в различие между кандидатами:

1. **Семейство событий с проверкой на исчерпывающесть** (§4.6, §4.7). Двадцать типов событий, пятнадцать корпоративных действий, шесть вердиктов приёмки, четыре уровня достоверности. Enum-ы с данными и `match` дают гарантию компилятора: добавленный вариант ломает сборку везде, где его не обработали. В Go сумма-типов нет — интерфейс с `type switch` молча проваливается в `default`, а структура с тегом делает невалидные состояния представимыми.
2. **`unknown` не должен быть нулём** (§4.9). Нулевые значения Go подталкивают ровно к тому, что спека запрещает: нулевая дата, пустая строка, `decimal.Zero` вместо честного «неизвестно». `Option<T>` в Rust заставляет обработать отсутствие.

3. **Разработку ведёт агент, а не человек.** Это усиливает первые два пункта. Забытая ветка `match`, нулевое значение вместо «неизвестно», перепутанные местами дата сделки и дата расчётов — в языке без этих гарантий всё это компилируется и уезжает как неверная цифра, обнаруживаемая через год. В Rust это ошибки сборки, то есть обратная связь агенту в том же цикле, точная и воспроизводимая.

**Границы этого аргумента.** Компилятор является механическим ревьюером **структуры данных и управления состоянием, но не финансовой семантики**. Он не поймает неверную формулу налога, неправильный basis, ошибочный момент признания дохода, не тот курс, выбранный не тот вариант enum или типобезопасный двойной счёт. Считать сильную типизацию заменой проверке смысла — опасная ошибка: она даёт ложное чувство надёжности. Именно поэтому §15 строится слоями, а не сводится к «компилятор проверит».

Принятая цена: более низкая скорость написания на старте, усугублённая тем, что агенты пишут на Rust хуже, чем на Go или TypeScript — меньше материала, выше сложность. Смягчается двумя обстоятельствами: сложная часть проекта приходится на простую часть языка (ядро — синхронный код над собственными данными, без нетривиальных времён жизни и без async; асинхронный слой ограничен axum и двумя HTTP-клиентами), а цена ошибки в налоговой базе платится деньгами, тогда как цена лишних итераций компиляции платится временем машины.

**Опыт владельца.** Больше опыта в Go, чем в Rust. В расчёт принято и перевешено тем, что код пишет агент: беглость владельца влияет на скорость чтения и ревью, а не на скорость написания.

### 17.1 Крейты

| Задача | Крейт |
|---|---|
| HTTP | `axum` + `tower` |
| SQLite | `rusqlite` (feature `bundled`) |
| Decimal (расчётные величины) | `rust_decimal` |
| Проведённые суммы | собственные newtype поверх `i64` / `i128` |
| Сериализация | `serde`, `serde_json` |
| XML MOEX ISS | `quick-xml` |
| OpenAPI | `utoipa` — спека порождается из типов обработчиков |
| HTTP-клиенты | `reqwest` |
| Логи | `tracing` |
| Ошибки | `thiserror` |
| Тесты | штатный `#[test]`, `proptest` (инварианты), `insta` (снапшоты отчётов) |

`utoipa` выбран потому, что спека, порождённая из типов обработчиков, устраняет расхождение **схемы данных**. Она не гарантирует совпадения поведения: коды ответов в рантайме, ошибки middleware, требования аутентификации, условные поля, бизнес-валидация, примеры и фактическая сериализация собственных типов остаются вне генерации.

Поэтому дополнительно требуются **чёрноящичные контрактные тесты**: поднять сервер, вызвать каждую задокументированную операцию, сверить запрос, ответ, код и требования аутентификации с порождённой спекой, плюс зафиксированные негативные сценарии. Для контракта, которым пользуется внешний агент, синтаксически верная, но поведенчески неверная спека означает, что агент будет чиниться по неверной подсказке.

### 17.2 Структура крейт

Полный граф зависимостей и правила внедрения — §3.2. Кратко:

```
iaam-core      доменные типы, журнал, проекции, доходность, налоги. Ни I/O, ни async, ни Mutex
iaam-store     SQLite, миграции, архивный бандл
iaam-market    клиенты MOEX и ЦБ, кэш, устойчивость, история цен
iaam-ingest    разбор источников, сверка, статусы достоверности
iaam-app       сценарии, порты, снимки, кэш — единственное место объектобезопасных портов
iaam-server    axum, REST, OpenAPI, аутентификация
iaam-cli       локальные команды
iaam-oracle    независимые эталонные реализации для тестов (§15.4), без зависимости на проекции
```

`iaam-server` и `iaam-cli` зависят от `iaam-app`, а не от адаптеров напрямую. Общего крейта `shared` / `common` / `utils` нет — обоснование в §3.2.

**`iaam-core` обязана оставаться библиотечной крейтой без знания о транспорте и хранилище.** Помимо тестируемости это сохраняет возможность собрать десктопное приложение на Tauri поверх того же ядра — специально под неё ничего не проектируется, но и дорога не закрывается.

### 17.3 Числовая политика

Задана в §6.6: три режима (точный, денежный, приближённый), запрет двоичной плавающей точки в доменных величинах, явная политика точности и остановки для итерационных методов, приближённые величины не входят в денежное тождество.

### 17.4 Веб-слой

Отдельный фронтенд на TypeScript, потребляющий тот же REST API (последний этап).

### 17.5 Перенос математики из `invest_calculator`

XIRR, DCF, ZCYC, календари и разбор ответов MOEX переносятся на Rust. **Это не механический перенос:** одновременно меняется числовая модель (§6.6) и создаются независимые эталоны (§15.4).

Календарных оценок этот документ не содержит намеренно. Планирование ведётся вертикальными срезами с приёмочными воротами: корпус эталонных значений XIRR; фикстуры денежных потоков по облигациям; фикстуры ZCYC; контрактные фикстуры MOEX. Срок появляется только после первого пройденного среза.
