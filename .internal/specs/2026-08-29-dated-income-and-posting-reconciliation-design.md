# Датированные факты дохода и сверка запланированных выплат

Закрывает бид `iaam-d8b.12.13`.

Родитель: `iaam-d8b` (E3 · Рынок и инструменты).
Опирается на завершённые E3.4.2 (график выплат, `iaam-d8b.4`), E3.4.1 (журнал и
проекция амортизации, `iaam-d8b.2`) и E3.4.5 (метрики §7.1, `iaam-d8b.12`).

---

## 1. Дефект

`MaterialIssue::ScheduledPostingNotReceived { instrument, date }` объявлен
(`crates/iaam-core/src/returns/mod.rs:261`), участвует в `is_defect`
(`:303`), доведён до DTO (`crates/iaam-server/src/dto.rs:1546`) — и **не
конструируется нигде**. Доказать неполучение запланированной выплаты нечем.

Двух половин не хватает, и обе — в проекции:

- `CashflowPlan.past` (`crates/iaam-core/src/rules/cashflow.rs:79`) несёт
  только **даты** запланированных выплат не позже `as_of`; читается лишь в
  тестах самого модуля;
- `Lot.received_to_date` (`crates/iaam-core/src/projection/lots.rs:100`) —
  одна **агрегированная сумма без дат**. Она заполняется в `add_received`
  (`:288`), которое вызывается из `apply_income` (`:566`). `apply_income`
  получает `event` целиком и **выбрасывает дату прямо здесь**.

По этой паре один пропущенный купон неотличим от полного получения при
ненулевом агрегате. Сверка по агрегату дала бы ложную тревогу на каждой
здоровой облигации с историей выплат.

## 2. Периметр

**Входит:**

- новый компонент проекции `IncomeLedger` — датированные факты дохода с
  привязкой к счёту и инструменту;
- расширение `CashflowPlan.past` до вида выплаты;
- версионированное правило сопоставления `PostingMatchV1`;
- конструирование `ScheduledPostingNotReceived` и нового
  `ScheduledPostingUnverifiable` с доведением до DTO, OpenAPI и контракта;
- `PROJECTION_VERSION` 3 → 4.

**Не входит:**

- производственный календарь рабочих дней (см. §5.1 — окно задаётся в
  календарных днях именно поэтому);
- налоговая трактовка датированных фактов (E5);
- импорт амортизации с брокерского канала (`iaam-mnz`, блокирован владельцем).

## 3. Компонент проекции `IncomeLedger`

### 3.1 Почему отдельный компонент, а не поле в `InstrumentLots`

`fold` (`crates/iaam-core/src/projection/mod.rs:326`) вызывает трёх
независимых читателей журнала поимённо — `balances.apply`, `book.apply`,
`flows.apply`. Общего механизма компонентов нет, и это **намеренно**: на
независимости читателей держится инвариант «сумма лотов равна позиции»
(§15.4). Четвёртый читатель — одна строка `income.apply(event)?`, а не
седьмой исчерпывающий диспетчер `EventKind`.

Поле внутри `InstrumentLots` было бы дешевле на вид, но связало бы
датированный факт с жизненным циклом лотов. Факт выплаты относится к
инструменту **на момент выплаты**, тогда как агрегаты лотов переносятся при
замещении (`Conversion`). Отдельный ledger этой связи не наследует.

### 3.2 Форма

```rust
struct IncomeLedger {
    entries: BTreeMap<LotKey, Vec<ReceivedPosting>>,
}

struct ReceivedPosting {
    event: EventId,
    date: Date,
    amount: Money,
    kind: PostingKind,
}
```

Ключ — существующий `LotKey (account, instrument)`: ровно та гранулярность,
на которую отвечает сверка.

Ряд **не делится по лотам**. Сверка отвечает на вопрос «пришла ли выплата», а
не «чья доля». `received_to_date` остаётся как есть и продолжает отвечать на
свой вопрос — пожизненную метрику; его пропорциональное деление по лотам
корректно и не трогается.

Хранится `EventId`, а не событие целиком: ссылка на журнал плюс необходимые
факты, не копия.

### 3.3 Источники фактов

Одних `Income`-событий недостаточно: в графике три вида выплат, и приходят они
разными типами событий.

| `PostingKind` | Событие журнала |
|---|---|
| `Coupon` | `EventKind::Income { instrument: Some(_), kind: Some(IncomeKind::Coupon), gross }` |
| `PrincipalReturn` | `CorporateAction::PartialRedemption { principal_returned_per_unit, compensation, .. }` — амортизация; `CorporateAction::Redemption { compensation, .. }` — погашение целиком |
| `OfferSettlement` | `OfferExerciseAction::Settled { gross, fee, accrued_interest, .. }` |

`Redemption` и `Settled` — выбытия: позиция уходит и сценарий по ней больше не
строится. Практический генератор ложных тревог — `PartialRedemption` при
сохранённой позиции.

`Income` с `kind: None` факта не порождает и помечает пару (счёт, инструмент)
как непроверяемую — см. §6. Это согласовано с существующим
`InstrumentLots::income_kind_unknown` (`lots.rs:142`), который по той же
причине отказывает в когортах.

`Income` с `instrument: None` игнорируется: без инструмента сверять не с чем.

### 3.4 Дата получения

`event.dates.cash_posted`, иначе `event.dates.paid`. Если нет ни того, ни
другого — факт датирован быть не может; см. `PaymentDateUnknown` в §6.

`EventDates::effective_date()` (`crates/iaam-core/src/dates.rs:103`) **не
используется**: его цепочка начинается с `settled` и падает до `trade`. Для
выплаты это не даты получения денег, и подстановка их молча сдвинула бы факт —
ровно тот вид выдумывания, который §4.9 запрещает.

Событие без даты — не гипотетика: `validate_structure` для `Income`
(`crates/iaam-core/src/event/mod.rs:197`) требует лишь одну положительную
денежную ногу и дат не требует вовсе.

### 3.5 Миграция снимков

`PROJECTION_VERSION` 3 → 4 (`projection/mod.rs:35`).

`advance` отвергает снимок с другой версией (`:278`), а
`recompute_is_worth_it` (`crates/iaam-app/src/scenarios/reports.rs:527`)
считает законным поводом пересчитать журнал целиком всё, кроме нарушения
инварианта. Старые снимки объявляются непригодными → полный пересчёт →
датированный ряд восстанавливается **за всю историю**, а не «с момента
внедрения».

`#[serde(default)]` для корректности не нужен — в отличие от
`amortisation_version` (`lots.rs:452`), где обратная совместимость снимка была
осознанным решением. Здесь она не нужна и была бы вредна: снимок без ряда
выглядел бы как позиция без единой полученной выплаты.

Срез журнала передаётся в `advance` **целиком** — оболочка не имеет права
отбирать «только новое» (`reports.rs:534-537`), иначе событие задним числом
исчезло бы из расчёта молча. Значит после пересчёта ряд полон.

## 4. Расширение графика

```rust
// было
pub past: Vec<Date>,
// стало
pub past: Vec<ScheduledPosting>,

pub struct ScheduledPosting {
    pub date: Date,
    pub kind: PostingKind,
}
```

Без вида выплаты сверка неработоспособна: в `past` попадают `Coupon`,
`PrincipalReturn` и `OfferSettlement` (`rules/cashflow.rs:64-69`), а фактами
купона их не подтвердить — возврат номинала приходит через `CorporateAction`,
не через `Income`. Сверка «даты `past` против купонных фактов» подняла бы
ложную тревогу на **каждой амортизируемой облигации и каждом погашении** —
ровно тот дефект, который эта работа устраняет.

Вид выплаты правилу уже известен: он есть в `ExpectedPosting`
(`rules/cashflow.rs:61`) и теряется только при укладке в `past`.

## 5. Правило сопоставления `PostingMatchV1`

Версионированное правило, попадающее в `AppliedRules` и `inputs_hash` — как
`quotation`, `accrued_interest` и `cashflow` (`returns/mod.rs:1181-1184`).
Версионируется **сопоставление**, а не хранение: хранение покрыто
`PROJECTION_VERSION`.

```rust
struct PostingMatchV1 { window_days: u16 }  // 21
```

### 5.1 Окно допуска: 21 календарный день

Запланированная дата и дата зачисления не совпадают почти никогда. Норматив
задаёт цепочку:

| Звено | Срок | Основание |
|---|---|---|
| эмитент → НРД | до 2 рабочих дней от даты выплаты | практика расчётов |
| НРД → депозитарий брокера | +1 рабочий день после поступления | порядок НРД с 12.01.2026 |
| депозитарий брокера → клиент | **не позднее 7 рабочих дней** после дня получения | ФЗ 39-ФЗ, ст. 8.7 — «иные депоненты», то есть обычный клиент |
| **итого** | **≈10 рабочих дней** | |

Депонентам-номинальным держателям и управляющим тот же пункт даёт не позднее
1 рабочего дня (при ненадлежащем исполнении эмитентом — 3), но конечный
владелец в эту категорию не попадает.

10 рабочих дней — это минимум 14 календарных (два выходных); если внутрь
попадают новогодние каникулы или майские, растягивается до 20–21 календарного.
Отсюда 21.

**Почему в календарных днях, а не в рабочих.** Производственного календаря в
ядре нет вовсе: `grep` по `crates/iaam-core` даёт лишь комментарий в
`valuation.rs:33`. Заводить его — отдельная работа с внешним источником,
который публикуется ежегодно. 21 календарный день — те же 10 рабочих,
растянутые через праздничный период, и правило версионировано, чтобы решение
можно было пересмотреть.

**Граница применимости.** Самый плотный реальный график — ежемесячный купон
(~30 дней). 21 < 30, то есть окно не дотянется до следующей выплаты, но запас
9 дней. Квартальный купон (~90 дней) — с большим запасом. При появлении бумаг
с более частой выплатой окно придётся сузить новой версией правила.

Источники:
[ст. 8.7 ФЗ 39-ФЗ (КонсультантПлюс)](https://www.consultant.ru/document/cons_doc_LAW_10148/017473a706c07dbfe90a15b9a3581cdb6f5e3967/),
[ст. 8.7 (ГАРАНТ)](https://base.garant.ru/10106464/61882faac1604f3e2a7c0e7e439d522f/),
[решение Совета директоров Банка России от 22.12.2023](https://cbr.ru/rbr/dir_decisions/rsd_2023-12-22_34_01/),
[изменение порядка НРД с 12.01.2026](https://goinvest.ru/news/sroki-vyplat-kuponov-po-cennym-bumagam-skoro-izmenyatsya/).

### 5.2 Условие совпадения

Факт закрывает запланированную выплату, если одновременно:

- `scheduled.kind == fact.kind`;
- `scheduled.date <= fact.date <= scheduled.date + window_days`.

Окно **одностороннее**: деньги приходят позже плана, но не раньше. Факт до
плановой даты плановую выплату не закрывает.

### 5.3 One-to-one, жадно

Запланированные выплаты и факты сортируются по возрастанию даты (при равенстве
— по `EventId`, чтобы порядок был полным и не зависел от порядка событий в
журнале). Далее: для каждой запланированной выплаты по возрастанию берётся
самый ранний ещё не израсходованный факт, удовлетворяющий §5.2. Факт
расходуется и второй раз не используется.

Один факт не должен закрывать две плановые даты — иначе пропуск в плотном
графике исчез бы. Жадность по возрастанию даёт детерминированный результат.

### 5.4 Граница владения

Проверяются только запланированные выплаты с датой не раньше **минимальной
`acquired` среди текущих лотов** пары (счёт, инструмент). Купон за период, в
котором бумаги ещё не было, владельцу не причитается, и требовать под него
факт — значит выдумывать дефект.

`CashflowPlan.past` этой границы не знает: правило строит поток от графика
выпуска, а не от истории владения. Границу накладывает сверка.

## 6. Проблемы отчёта

```rust
ScheduledPostingNotReceived {
    account: AccountId,      // новое
    instrument: InstrumentId,
    date: Date,
    kind: PostingKind,       // новое
}

ScheduledPostingUnverifiable {   // новый вариант
    account: AccountId,
    instrument: InstrumentId,
    reason: UnverifiableReason,
}

enum UnverifiableReason {
    AcquisitionDateUnknown,
    IncomeKindUnknown,
    PaymentDateUnknown,
    HistoryStartsAfterSchedule,
}
```

`account` добавляется в `NotReceived`, потому что сегодня одна бумага на двух
счетах даёт две неразличимые проблемы. `kind` — потому что «не пришёл купон» и
«не пришёл возврат номинала» требуют от владельца разных действий.

### 6.1 Когда сверка недоказуема

| Причина | Когда |
|---|---|
| `AcquisitionDateUnknown` | границу владения (§5.4) провести нечем: `unpriced > 0` либо у лота `acquired == None` |
| `IncomeKindUnknown` | по паре есть `Income` с `kind: None` — факты на график не ложатся |
| `PaymentDateUnknown` | по паре есть событие одного из видов §3.3 без `cash_posted` и без `paid` |
| `HistoryStartsAfterSchedule` | запланированная выплата прошла границу владения (§5.4), но её дата раньше начала журнала |

Последняя причина не поглощается границей владения и достижима именно потому,
что `acquired` берётся из **заявленной** даты сделки, а не из положения
события в журнале. `OpeningPosition`, записанное 2026-01-01 с
`dates.trade = 2020-05-01`, даёт `acquired = 2020-05-01`: купоны 2020–2025
границу владения проходят, но фактов под них в журнале нет и быть не может.
Без этой причины они дали бы массовую ложную тревогу — ровно то, что бид
требует не допустить.

### 6.2 `is_defect`

| Причина | `is_defect` | Обоснование |
|---|---|---|
| `AcquisitionDateUnknown` | `true` | дыра в данных, чинится дозагрузкой фактов |
| `IncomeKindUnknown` | `true` | то же; согласовано с `CohortGap::IncomeKindUnknown` |
| `PaymentDateUnknown` | `true` | то же |
| `HistoryStartsAfterSchedule` | `false` | зеркалит `HistoryStartsAt`: факт о периоде, а не дефект |

`ScheduledPostingNotReceived` остаётся `true`: там действительно чего-то не
хватает.

Раскладка не произвольна. `is_defect == true` делает ровно одно — ставит
`DataQualityStatus::Incomplete` (`returns/mod.rs:1219`, `:1925`); числа не
прячет, позицию из стоимости не убирает, `nav_coverage` не меняет. При этом
`Incomplete` уже частое состояние: его ставит любая позиция без пригодной цены
(`:1925`).

**Проверенная поправка.** Первоначально предполагалось, что
`AcquisitionDateUnknown` всегда дублирует уже существующий
`RestoredWithoutBasis` и потому выбор `true`/`false` ничего не меняет. Это
неверно. `unpriced > 0` действительно возникает только из
`OpeningPosition { cost_basis: None }` (`lots.rs:962`), что помечает счёт как
restored. Но `CohortGap::AcquisitionDateUnknown` возвращается и когда у
обычного лота `acquired == None` (`lots.rs:344`), а `Lot.acquired` —
`Option<TradeDate>` (`rules/lot_disposal.rs:38`), куда `apply_trade` кладёт
`event.dates.trade` как есть (`lots.rs:619`); схема отсутствие даты допускает
(§4.9, `dates.rs:57`). Такая покупка счёт в `restored_accounts` не добавляет, и
отчёт мог бы остаться `Complete`. Поэтому `true` здесь несёт собственный вес.

### 6.3 Транспорт

Оба варианта доводятся до `crates/iaam-server/src/dto.rs`, OpenAPI и
контрактного теста. Изменение формы `ScheduledPostingNotReceived` (добавление
`account` и `kind`) — правка контракта; вариант не публиковался ни в одном
ответе, потому что никогда не конструировался.

## 7. Заслоны

**Регрессия — главный критерий приёмки бида.** Облигация с пятилетней историей
полученных купонов, факты со сдвигом 1–7 дней от плановых дат: **ноль тревог**.

Остальные:

- **Амортизируемая облигация.** `PartialRedemption` закрывает
  `PrincipalReturn`, купоны закрывают `Coupon` — ноль тревог. Без расширения
  `past` (§4) этот тест красный: возвраты номинала не находят купонных фактов.
- **Пропуск в середине ряда.** Один купон не пришёл → ровно одна
  `NotReceived` с правильными счётом, инструментом, датой и видом; соседние
  выплаты не задеты.
- **One-to-one (§5.3).** Два факта в одном окне не закрывают две плановые
  даты, если вторая вне своего окна.
- **Граница окна.** Факт на `scheduled + window_days` закрывает выплату, на
  `scheduled + window_days + 1` — не закрывает. Факт раньше плановой даты не
  закрывает.
- **Граница владения (§5.4).** Купон с плановой датой до `acquired` тревоги не
  даёт.
- **Восстановленная история (§6.1).** `OpeningPosition` с заявленной датой
  сделки на пять лет раньше первого события журнала даёт
  `Unverifiable { HistoryStartsAfterSchedule }` и **ни одной** `NotReceived`.
- **Покупка без `event.dates.trade`** → `Unverifiable { AcquisitionDateUnknown }`,
  отчёт `Incomplete`, при том что `RestoredWithoutBasis` не выставлен.
- **`Income` без `cash_posted` и `paid`** → `Unverifiable { PaymentDateUnknown }`.
- **Две пары (счёт, инструмент) с одной бумагой** дают две различимые
  проблемы.
- **Свойство:** результат сверки не зависит от порядка событий в журнале.
- **Свойство:** повторная проекция того же журнала даёт тот же результат
  (§3.1, §15.3).
- Мутационный заслон по новым модулям — по порогу проекта.

## 8. Отложено

- Производственный календарь рабочих дней и окно в рабочих днях (§5.1).
- Сужение окна при появлении бумаг с выплатой чаще ежемесячной (§5.1).
- Потребление датированных фактов налогами (E5): ряд заводится в форме,
  пригодной для §214.1, но налоговая трактовка в периметр не входит.
